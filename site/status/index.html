    What is not measured

    • No independent or third-party evaluation. Every batch, including the held-out one, is hand-written in this repository by the same author as the engine. heldout_v10 was a real out-of-sample estimate of those payloads; its one-shot 38.6% recall / 0.0% FPR is frozen in heldout_v10_report.json, while the current engine measures 100%/0.0% on the same batch and the in-sample 100%/0% rows above are not. Neither number says anything about traffic that was not imagined: no customer access log has ever been measured against this engine.
    • No comparison against real WAF products. The Python harness (run_benchmark.py) runs local stand-ins written for this repository. Rows named Coraza, SafeLine, ModSecurity or "probabilistic NLP" are reimplementations, not those products. They must never be cited as vendor benchmarks.
    • No production soak. No staged rollout, no traffic replay at scale, no long-running memory or rule-update testing.
    • No TLS or WebSocket handling in the standalone proxy. TLS terminates in front of it; WebSocket upgrades are rejected.
    • Prebuilt artifacts under dist/ and releases/ are stale. They were built before the claims were corrected and still contain the old banner text. Rebuild or delete them before publishing; do not ship them as current.

    How to reproduce

    Two different numbers get quoted in these documents and they come from two different corpora. Do not expect one command to print the other one:

    what you run corpus benign controls what it prints status of that corpus
    cargo run --release -- benchmark -r 10000 corpus/independent_v1.json 16 100% recall, 0.0% FPR in-sample regression floor: every miss in it was used to fix the engine
    ../target/release/satbench.exe --corpus benchmarks/real_comparative/corpus/heldout_v10.jsonl heldout_v10.jsonl (70 attacks, 44 benign) 44 one-shot: 38.6% recall, 0.0% FPR (corpus/heldout_v10_report.json); current engine: 100%/0.0% post-tuning diagnostic (corpus/heldout_v10_post_tuning_report.json) current behaviour is the post-tuning diagnostic; the frozen one-shot estimate stays 38.6%/0.0%
    cargo run --release --bin satbench -- --corpus benchmarks/real_comparative/corpus/unified_v1.jsonl unified_v1.jsonl floors — 100% recall, 0.0% FPR on in-sample splits regression floor, not an estimate

    So the 0.0% false-positive rate on 44 controls above is the held-out measurement. tests/comparative_corpus_test.rs::heldout_v10_reproduction_matches_the_published_report re-derives it in-process. Batch v10 has since been spent by the protocol/DSL detector iteration: the engine now clears all 70 attacks, so the test asserts the one-shot figures remain intact as provenance and that live behaviour still matches corpus/heldout_v10_post_tuning_report.json — if the engine ever blocks a different set of v10 cases, the test fails. Per maintainer decision no heldout_v11 will be produced; the 38.6%/0.0% one-shot remains the only publishable held-out estimate. tests/heldout_v2_measurement_test.rs is gated behind an environment variable and now documents a spent batch.

    tests/comparative_corpus_test.rs calls the engine in-process — no HTTP, no proxy, no deployed host — and pins all three numbers as unit tests. Its held-out test asserts the reproduction, not the quality: if the engine ever blocks a different set of held-out cases, the test fails and says the batch is spent, which is the only way a held-out estimate can stay trustworthy.

    # The frozen one-shot estimate lives in corpus/heldout_v10_report.json
# (38.6% recall / 0.0% FPR). Re-running the corpus now prints the current
# engine behaviour (100%/0.0%) recorded in
# corpus/heldout_v10_post_tuning_report.json.
../target/release/satbench.exe --corpus benchmarks/real_comparative/corpus/heldout_v10.jsonl \
    --out benchmarks/real_comparative/results/satguardian/verdicts_heldout_v10_post_tuning.jsonl

# Detection regression (both in-sample corpora)
cargo test --test independent_corpus_test -- --nocapture

# The same measurements as in-process unit tests: no HTTP, no proxy, no deployed host
cargo test --test comparative_corpus_test -- --nocapture

# Full Rust suite
cargo test

# In-memory benchmark over the in-sample corpus
cargo run --release -- benchmark -r 10000

# Python reference harness (local stand-ins, in-sample)
python run_benchmark.py 1000

    Control boundary (what the paid tier actually does)

    The product promise is: free, local protection; paid, ongoing review, update proposals and explanations — without giving up control of the WAF. As of 2026-11-04 the code matches that:

    • auto_sync_enabled defaults to false (src/config.rs), and the shipped waf_config.toml leaves it off. Cloud review runs only if you turn it on or invoke satguardian-waf sync-simplify / POST /api/waf/sync-simplify.
    • A review uploads recorded u128 feature vectors, not raw requests, and what comes back is stored in dynamic_clauses with applied = 0. Startup loads applied = 1 rows only.
    • A clause enters the engine after an explicit approval (satguardian-waf clauses apply <id>, or POST /api/waf/clauses/{id}/apply behind the admin token). reject deletes only unapplied proposals. Approved clauses are registered in an RwLock-guarded table capped at 4,096; there is no lock-free swap and no automatic apply anywhere in the client.
    • The Boolean minimizer (exactor-core-v128) is not a dependency of this crate and is not in any client artefact; minimization happens on the service side.
    • satguardian-advisor.py has no batch-approval option. Every proposal is decided one at a time by the operator running it.

    tests/docs_claims_test.rs::cloud_review_stays_opt_in_and_never_applies_by_itself and tests/clause_approval_test.rs fail if any of that regresses.

    Why this file exists

    Earlier versions of this repository published a benchmark that:

    • capped perfect accuracy at 99.9% and floored zero error rates at 0.1%;
    • labelled Python regex stand-ins as "Coraza WAF (OWASP CRS v4)" and "SafeLine WAF (Chaitin T1K)";
    • derived "3.38x faster", "15.0x faster" and "reduced false negatives by N percentage points" headlines from those stand-ins;
    • presented the numbers as production evidence.

    Those claims were fabricated or misleading. The cap/floor logic is gone, the stand-ins are labelled, and the Rust benchmark now refuses to run without the versioned corpus. The guardrail tests in tests/docs_claims_test.rs fail the build if the banned claims or unlabelled comparisons return.

    Treat a green test suite as "no known regressions on pinned inputs", not as "safe for production".
